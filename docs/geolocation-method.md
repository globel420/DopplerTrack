# DopplerTrack location method: research and implementation path

**Mission:** estimate a video's recording area by detecting aircraft-like Doppler curves in its audio, matching them to historical aircraft trajectories, and reporting an uncertainty region. A spectral curve alone is not a location.

The current DopplerTrack build includes an experimental, opt-in flight-track/location matcher. The ADSB.aero connector is disabled by default in source; the production deployment enables it after reviewing the public service's best-effort terms and request limits. One test query was sent to the provider on 2026-11-04 to check parsing, and it hit the 50-flight limit (see the [optimization list](optimizations.md)); no user job has queried it. A synthetic two-flight geometry case passes, which checks model consistency but does not establish real-world accuracy.

## End-to-end explanation

DopplerTrack treats the video as a container for sound. It currently **does not inspect the picture** for landmarks, buildings, roads, or sky features.

1. **Validate and decode.** `ffprobe` checks for a readable video stream and enforces the 4 GiB and one-hour limits. The browser sends resumable 32 MiB chunks so the full file stays below the reverse proxy's per-request ceiling. FFmpeg extracts mono audio; clips longer than 10 minutes are analyzed in 60-second windows to bound memory. The source file and intermediate output are subject to 24-hour cleanup.
2. **Screen the audio.** The quick scan uses a spectrogram to estimate audio level, clipping, and whether any smooth narrowband frequency ridges are visible. It can say that a recording is likely suitable for further analysis, inconclusive, or unsuitable. These are screening labels, not aircraft classifications.
3. **Measure candidate curves.** The deep scan computes a higher-resolution time-frequency representation and follows narrow frequency peaks over time. It records measurements such as start/end frequency, slope, fit, and prominence. It looks for possible harmonic ratios, then treats detected harmonics as one family during location matching. Sirens, engines, machinery, wind, voices, reflections, and codecs can still create plausible-looking ridges.
4. **Anchor the clip.** Matching requires the clip's recording start time with an explicit UTC offset, a user-supplied clock uncertainty, and a bounded search circle. The upload time is never used as the recording time. The circle is an input constraint, not an inferred result.
5. **Retrieve historical tracks only with opt-in.** The separate checkbox and the server's `ADSB_HISTORY_ENABLED=true` setting must both permit lookup. One request sends the time, duration, clock uncertainty, and search area to adsb.aero; it does not send audio or video. The query circle is expanded by 60 km and the time window includes the clip, clock uncertainty, and a propagation margin. A Redis key limits the service to one query every five minutes across workers. The adapter accepts no more than 50 flights/8 MiB and abstains if the response is truncated. This API currently accepts clips up to 10 minutes; longer videos are fully scanned for audio but never trigger a flight query. Historical tracks are sourced from ADSB.lol; the UI and report carry attribution and the ODbL 1.0 link.
6. **Fit tracks to sound.** For each receiver point in a coarse-to-fine grid, the matcher predicts a received frequency curve for each available flight. It converts aircraft positions to WGS84/ECEF, estimates motion within each observed segment, applies a sound-travel delay, fits one unknown source tone per ridge, and fits one shared recorder-clock offset across the event. Track gaps over 60 seconds are not interpolated across.
7. **Gate the location result.** The current code needs two distinct flight IDs, a median relative frequency residual no greater than 1.5%, and no similarly good separated grid alternative. If any gate fails, data are missing, or provider results are incomplete, it returns `Location undetermined`. A passed result is labeled an experimental coordinate; grid spacing is not a confidence interval and residuals are not probabilities.

The candidate curve and historical track are evidence to compare, not proof. This prototype's synthetic two-flight test generates and then recovers a curve using the same physical model; it does not measure accuracy on a real recording. No independent known-location evaluation has established a false-location rate, a confidence level, or a usable real-world error radius.

## What the method uses

1. **Audio evidence.** Decode the video's audio, detect moving narrowband ridges, group related harmonics, and keep measurements plus diagnostics. Do not accept the strongest path through a spectrogram automatically: noise-only audio can always produce a “best” ridge. A current independent prototype uses a Viterbi ridge detector and reports that false fits required additional SNR gates; it still describes its location pipeline as experimental and has no accepted blind real-location result ([DOPPLERGEIST README](https://github.com/1337isnot1337/DOPPLERGEIST), [real-data verification](https://github.com/1337isnot1337/DOPPLERGEIST/blob/main/docs/verification/WORKER_E2E_2026-11-03.md)).
2. **Recording-time evidence.** Historical matching requires a defensible recording date and clock window. A video metadata timestamp can be shown as a hint, but the user must confirm it. The upload date is never a substitute. DopplerTrack now accepts ISO 8601 time only when it includes a UTC offset; the backend normalizes that explicitly supplied time to UTC.
3. **Flight data.** Historical ADS-B trajectories are available from the ADSB.lol daily archive under ODbL 1.0. DopplerTrack's optional connector uses the public `adsb.aero` geometry/time API, whose documentation says it ingests the ADSB.lol archive. It asks the user before sending recording time/duration/clock uncertainty/search circle, sends no media, requests one modest page, and refuses to locate from a truncated page. A Redis-backed global limiter allows at most one provider query every five minutes. The API guide says it is unauthenticated, asks callers to use one broad query and avoid polling, and notes that it runs on one box. It does not publish a production SLA or explicit hosted-service license. The source default remains off; production enables the flag after this service review, but no live DopplerTrack history query has been made ([API guide](https://adsb.aero/llms.txt), [live API docs](https://adsb.aero/api/docs), [ADSB.lol archive](https://www.adsb.lol/docs/open-data/historical)).
4. **Location fit.** For each plausible receiver location and flight track, predict the curve that microphone would hear and compare it with the measured ridge. Include sound travel time, aircraft motion, altitude, and the sound speed. Fit an unknown source tone per ridge and one shared recording-clock offset. The present prototype uses a coarse-to-fine bounded grid, WGS84/ECEF positions, a robust median-tone fit, and one-to-one assignment between ridges and distinct flight IDs. Ridges with detected harmonic ratios are collapsed to one candidate so a single tonal family cannot count as multiple passes. It requires two distinct matched flight IDs and residual/separation gates before returning an experimental coordinate.

The physical model uses aircraft emission time `τ`, receiver location `o`, aircraft position `x(τ)`, velocity `v(τ)`, sound speed `c`, and range `r(τ) = ||x(τ) − o||`. With positive radial velocity defined as receding:

```text
u_r(τ) = dot(v(τ), x(τ) − o) / r(τ)
arrival_time t = τ + r(τ) / c
predicted_frequency f(t) = f0 * c / (c + u_r(τ))
```

The solver iterates the arrival-time equation and uses radial velocity at **emission** time. Substituting receiver time changes the curve shape. It interpolates only within an observed ADS-B segment; gaps over 60 seconds remain separate. The current prototype uses pressure altitude as an approximate ellipsoidal height and assumes sea-level receiver elevation and fixed sound speed. The independent DOPPLERGEIST methodology documents this model, WGS84/ECEF geometry, trajectory-gap handling, and the unknown-tone fit ([methodology](https://github.com/1337isnot1337/DOPPLERGEIST/blob/main/docs/METHODOLOGY.md)).

## Why one pass may not locate the camera

A Doppler curve constrains relative motion. Without an absolute time, a single pass can retain an along-track ambiguity; a known clock narrows it, and independent passes with one shared clock can add constraints. Multiple passes still do not guarantee a unique answer. A peer-reviewed acoustic localization experiment used seven synchronized microphones for 3D localization of a GPS-equipped radio-controlled aircraft; a separate single-array study combines Doppler-derived closest-approach parameters with array phase/direction evidence. These are not validation of a single phone recording ([2016 experimental study](https://upcommons.upc.edu/server/api/core/bitstreams/a00f4ad0-dc9b-4b95-b88c-520b7b1a5184/content), [JASA study](https://pubmed.ncbi.nlm.nih.gov/27106332/)).

Engine tone can change with RPM, and aircraft can turn or accelerate. Sound speed, wind, ground reflections, microphone response, codec processing, unknown clock error, and gaps in ADS-B coverage can all degrade the fit. A 2026 flyover-array study estimates a tone using ADS-B geometry but relies on a steady approach/engine assumption; the paper's array and controlled recording setup differ from consumer video ([study](https://link.springer.com/article/10.1007/s13272-026-00962-2)).

**Current implementation:** use `adsb.aero` for an explicitly opted-in, one-request experimental query only when the server operator enables `ADSB_HISTORY_ENABLED=true`. The production deployment enables this flag after service review. A deep scan without a sufficiently long measured ridge does not reserve provider capacity or send a query. The app does not silently download the whole-day global archive. The provider query sends recording time, video duration, clock uncertainty, and the user-specified circle; it does not send source media. The interface and report attribute the ADSB.lol historical data and link ODbL 1.0. The free query service is best-effort; no production capacity or availability is claimed. One test query has been sent, and no user job has queried it.

## Geolocation workflow

1. Decode and retain the original media only for the documented short retention period; derive an audio-only working stream with source-rate and clock metadata.
2. Detect candidate curves and harmonics. Record band, ridge SNR, observation times, fit residuals, missed/ambiguous paths, and why an event was rejected.
3. Require the user's explicit recording time with UTC offset, clock uncertainty, and search-circle center/radius. Never infer from upload time. A separate consent checkbox is required before sending these query fields to the external historical service.
4. Query the UTC interval and geography once. The query circle adds 60 km to the user's receiver-area radius to cover sound travel; the time window adds up to 180 seconds for propagation. The connector caps the response at 50 flights / 8 MiB, retains segment gaps, and returns no location if the response is truncated or the provider fails.
5. Collapse detected harmonic families, then for a coarse-to-fine receiver grid calculate retarded-time Doppler curves for each candidate flight. Fit one source tone per measured ridge and a shared clock offset; compare residuals in Hz. Assign each ridge to at most one distinct flight ID. The current display gate requires two flight IDs and a median relative residual at or below 1.5%, plus a separated-location check.
6. Show a coordinate only as an **experimental candidate** when those code gates pass. The reported grid spacing is not a confidence interval. Do not translate residuals into probabilities or imply calibrated location accuracy.
7. Return `Location undetermined` when time, region, ridge quality, provider coverage, physical-fit residuals, independent flights, response completeness, or separation from alternative hypotheses is inadequate.

## Validation before publishing locations

- Build a blind set of videos recorded at known coordinates with independently logged UTC time and multiple aircraft passes. Keep coordinates and flight identity out of the search inputs.
- Measure ridge/event precision and recall, correct-flight rank, geodesic location error, coverage of reported uncertainty regions, false confident-location rate, and abstention rate. Split train/tune/evaluation recordings by site, date, and aircraft event.
- Include one-pass versus multi-pass cases, clock offsets, turning/accelerating tracks, missing ADS-B segments, noisy clips, engine-speed changes, sirens, road traffic, wind, ground reflections, and compression.
- Do not present a location as reliable until real, held-out, known-truth evaluations support the stated error and confidence interval. Current public prototypes do not establish that bar: DOPPLERGEIST reports no accepted blind real localization in its current project status.
- The included synthetic trajectory test checks that the implemented equations can recover a self-generated two-pass case; it uses the same forward model and is not an independent accuracy test. Real aircraft audio, service capacity, and a user-job lookup through the deployment connector remain unverified.
